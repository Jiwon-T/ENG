# B — 문자 템플릿 영구 저장·동기화 파일럿

작성일: 2026-10-08 (Asia/Seoul). 이전 A 설계의 첫 구현 구간입니다. 구현·로컬 모의 검증과 운영 이전 완료는 별개입니다.

## 범위와 기본 상태

- 기존 `main` 학원 문자 템플릿 DB 한 종류만 대상입니다. 원본 DB는 현재 문자 기능이 사용하는 `ec10d0f1-c79a-8312-946b-811e86041ee2`입니다. 요청 본문으로 학원/DB를 바꿀 수 없습니다.
- 신규 템플릿 생성·삭제, 다른 자료 이전, 학생 계정/PIN/리포트 연결 변경은 포함하지 않습니다. 기존 템플릿의 이름과 본문만 앱에서 수정합니다. 대상 select와 다른 Notion 속성·관계는 보존합니다.
- 문자는 발송하지 않았고 Make·Notion·Firestore·배포 설정을 변경하지 않았습니다. 모의 응답에서만 반영/오류/복구를 실행했습니다.
- `MESSAGE_TEMPLATE_READ_MODE` 기본은 `notion`, `MESSAGE_TEMPLATE_SYNC_ENABLED` 기본은 `false`입니다. 설정 누락도 기존 조회와 작업 실행 차단을 유지합니다. Firestore 조회를 켠 뒤 최초 가져오기가 미완료면 오류로 멈추며 Notion으로 조용히 되돌아가지 않습니다.
- 화면은 관리자 설정 → **문자 템플릿 영구 저장·동기화 열기**입니다. main 학원의 전역 관리자만 이전·수정·충돌 처리·복원합니다. 기존 담당 학생의 문자 기능 권한은 그대로입니다.

## 저장·작업·이력

`messageTemplateSources`: 학원+원본 DB+정규화한 페이지 UUID의 SHA-256 키를 사용합니다. 사용자별 복사본은 만들지 않습니다. 원본 필드 중 이름/본문/대상/보관 여부만 저장하며 원본 DB·페이지 ID를 유지합니다.

`messageTemplateJobs`: 앱 수정과 같은 트랜잭션으로 등록하는 불변 요청입니다. 작업 ID·예상 자료 버전·기준 원본 해시·반영할 값을 보존합니다. 실패해도 앱 값은 유지합니다. 반영 대기/실패 중 새 앱 수정은 이전 대기 작업을 대체합니다. 실행 중 잠금이 살아 있으면 수정은 잠시 거절하고 입력은 유지합니다.

`messageTemplateSync`: 원본 공통 잠금, 최초 기준 시점 T0, Notion 페이지 cursor, 변경분 기준 시점, 마지막 성공 및 실패 코드, 보관 대조 cursor입니다. 웹앱 사용자 수에 비례해 작업을 복제하지 않습니다.

`messageTemplateHistory`: 수정 전후와 충돌 당시 원본 값, 버전, 주체, 시각을 보존합니다. 화면에서 최근 10개 이력을 보고 기존 이름/본문을 새로운 버전으로 선택 복원할 수 있습니다. 복원도 현재 버전 검사와 동일 작업 등록을 거칩니다. `retainUntil`은 90일 보존의 안내값이며 TTL·자동 삭제를 설정하지 않았습니다.

네 컬렉션은 클라이언트 읽기/쓰기를 금지합니다. 서버는 고정 원본과 권한을 검사합니다. 본문·충돌 값·요청 payload·이력의 값은 인덱스에서 제외하는 설정을 준비했습니다. 기존 다른 컬렉션의 권한 정책은 바꾸지 않았습니다.

## 이전·가져오기

1. **dry-run**: 한 번에 원본 20개와 해당 ID의 앱 저장본만 비교합니다. 쓰기는 0입니다. 다음 페이지 버튼으로 전체를 확인하며 페이지별 신규/동일/갱신/확인 필요를 보고합니다. 전체 건수라고 표시하지 않습니다.
2. **최초 가져오기**: T0와 cursor를 저장합니다. 한 요청당 최대 20개를 처리하고 성공한 후에 cursor를 전진합니다. 반복 클릭은 이어서 처리합니다. 임의의 전체 삭제·병합은 하지 않습니다.
3. **추가 변경분**: 최초 전체 조회가 끝나면 T0 이후 변경분을 겹쳐 가져옵니다. 완료 전에는 `ready`가 true가 되지 않습니다.
4. **일반 변경분**: 마지막 성공 기준 시각부터 2초 겹쳐 조회합니다. 조회된 페이지 ID만 비교하고, 필드 해시가 같으면 템플릿/내용 이력을 다시 쓰지 않습니다. 전체 Firestore 페이지 목록을 읽지 않습니다. 잠금·진행 기록 쓰기는 별도로 발생합니다.
5. **원본 상태 점검**: 저빈도 실행에서 앱 문서를 cursor로 최대 5개씩 읽고 원본을 확인합니다. 명시적 archived/in_trash만 보관 처리합니다. 403/404는 접근/삭제가 확정되지 않은 상태로 표시하고 앱 값을 유지합니다. 실제 원본 삭제와 권한 해제의 구분은 운영 확인이 필요합니다.

운영 초기 dry-run 결과와 가져온 필드 값/원본 연결을 확인한 뒤 조회를 전환합니다. 정렬 중 원본 변경, API cursor 만료 등 운영 조건은 실자료 시험이 필요합니다. cursor 오류가 발생하면 진행 기록을 임의 삭제하지 말고 원인과 마지막 처리 위치를 확인합니다.

## 충돌·재시도

- 앱 저장: 값과 요청/이력을 원자적으로 저장합니다. 같은 요청 ID 재전송은 동일 의도만 허용합니다. 오래된 자료 버전은 거절합니다.
- worker: 현재 앱 버전·작업 잠금을 확인하고 원본을 GET합니다. 원본이 반영할 값과 같으면 성공만 기록하고 PATCH하지 않습니다. 원본이 기준값과 다르면 충돌로 남깁니다.
- PATCH는 기존 페이지의 이름/본문만 변경하며 새 페이지를 만들지 않습니다. 응답 유실 후 같은 페이지 값을 확인하므로 중복 생성은 없습니다.
- 실패는 안전한 코드만 남깁니다. 일시 실패는 지수 지연, 최대 8회 후 관리자 확인을 요구합니다. 구성/스키마/권한 오류는 자동 재시도를 중단합니다. 화면의 다시 시도는 불변 작업을 다시 대기 상태로 등록합니다.
- 양쪽이 바뀌면 앱 값과 원본 캡처를 함께 보존합니다. 관리자가 원본 가져오기 또는 앱 값 유지·다시 반영을 선택합니다. 다시 반영 직전에도 원본 기준을 확인합니다. 원본이 보관된 경우 앱 선택으로 자동 복원하지 않습니다.
- Notion은 원자적 조건부 쓰기를 제공하지 않으므로 직접 수정과 PATCH가 정확히 겹치는 경합을 완전히 차단한다고 보장하지 않습니다. 반영 대기 중 직접 수정은 피하고, 필요 시 충돌 확인 후 처리합니다.

## 별도 작업 서버 — 사용자가 배포

웹앱 서버에 cron을 추가하지 않았습니다. `scripts/template-sync-worker.ts`를 별도 private Cloud Run 서비스로 배포하는 준비물만 제공합니다.

먼저 `node scripts/prepare-template-worker-context.mjs`를 실행합니다. 출력된 `.template-worker-context/<UUID>` 폴더에는 명시한 소스·패키지 파일·공개 Firebase 설정만 복사됩니다. 운영 .env/키/자료/ZIP/Git 이력/테스트는 포함하지 않습니다. 이 폴더에서 `scripts/template-worker.Dockerfile`을 지정해 이미지 빌드합니다. 소스 루트 전체를 Cloud Build에 업로드하지 않습니다. Docker 빌드와 클라우드 배포는 이번 작업에서 실행하지 않았습니다.

worker에는 다음만 설정합니다.

| 변수 | 설정 |
| --- | --- |
| FIREBASE_PROJECT_ID | 현재 실제 프로젝트 ID |
| FIRESTORE_DATABASE_ID | 현재 사용 중인 명명 DB ID. 기본 DB fallback 없음 |
| NOTION_INTEGRATION_TOKEN | Secret Manager의 기존 원본 접근 토큰 |
| MESSAGE_TEMPLATE_SYNC_ENABLED | 운영 준비 확인 후 `true` |
| MESSAGE_TEMPLATE_WORKER_SECRET | 32~256자 비밀값. 브라우저에 전달하지 않음 |
| PORT | Cloud Run 런타임 제공 |

worker Firestore 인증은 Cloud Run 서비스 계정/ADC를 사용합니다. 웹앱 Firebase private key를 복사하지 않습니다. 실제 프로젝트·Enterprise DB 모드·리전·IAM 접근을 확인해야 합니다. 전용 서비스 계정에 필요한 Datastore 접근과 해당 Secret 접근만 부여하고, 광범위한 Editor/Owner는 부여하지 않습니다.

Cloud Run은 **인증 필수**로 유지합니다. Scheduler 전용 계정에만 Run Invoker를 부여합니다. `POST /run`은 인프라 OIDC 인증과 `X-Template-Worker-Secret`을 함께 사용합니다. 일반 Firebase 로그인 토큰으로 호출하는 공개 API가 아닙니다.

| 작업 | 권장 실행 | JSON 본문 |
| --- | --- | --- |
| 반영·실패 복구 | 1분마다, 지연을 허용하면 5분 | `{ "mode": "push" }` |
| Notion 예외 수정 보완 | 하루 1회, 예: 05:00 Asia/Seoul | `{ "mode": "pull" }` |
| 삭제·보관·접근 대조 | 주 1회, 예: 일요일 05:30 | `{ "mode": "reconcile" }` |

push는 한 번에 만기가 된 작업 최대 5개를 처리합니다. pull은 한 번에 최대 5페이지 처리하고 남은 cursor는 저장합니다. 이후 push 복구 실행은 **이미 시작된** 가져오기/대조만 이어서 처리합니다. idle 상태의 push는 새 Notion 조회를 시작하지 않습니다. 권장 request timeout 300초, 최소 인스턴스 0, 최대 인스턴스와 동시성은 우선 1로 제한합니다. 이 설정/주기는 실제 배포하지 않았습니다.

## 조회 전환과 복귀

1. 웹앱은 `MESSAGE_TEMPLATE_READ_MODE=notion`으로 먼저 적용합니다. 새 기능만 추가되며 기존 조회는 유지됩니다.
2. 인덱스와 보안 규칙을 사용자가 적용하고 준비 완료를 확인합니다. 기존 인덱스를 삭제하지 않습니다.
3. 관리자 dry-run → 소규모 가져오기 → 전체 및 catch-up 완료 → 저장 필드/원본 ID/보관 상태 대조를 수행합니다.
4. 별도 worker를 private으로 배포하고 템플릿 수정 1건의 실패/재시도/충돌을 실자료에서 확인합니다. 문자는 보내지 않습니다.
5. 검증 후 웹앱 `MESSAGE_TEMPLATE_READ_MODE=firestore`로 바꾸고 재배포합니다. 메시지 목록/준비는 저장 템플릿을 사용합니다. 학생 원본/연락처·권한/발송 전 확인은 기존 경로를 유지합니다.
6. 문제 발생 시 worker 자동 실행을 끄고 대기 작업·앱 최신값을 확인합니다. 앱에만 저장된 미반영 수정이 있으면 이를 보존하고 정리한 뒤 read mode를 `notion`으로 복귀합니다. 단순 복귀가 미반영 앱 내용을 Notion에 옮기는 것은 아닙니다. 앱 저장본과 이력을 삭제하지 않습니다.

새 템플릿 조회는 기존 500개 상한을 보존하고 초과 시 오류를 냅니다. 관리자 관리 목록은 20개 cursor 페이지입니다. 500개를 넘는 실제 원본이면 일반 문자 목록의 페이지 선택 개선을 별도 진행한 뒤 전환해야 합니다.

## 모의 측정 — 운영 비용/속도 아님

| 경로 | 이전 Notion 요청 | Firestore 전환 후 | 추가 Firestore 작업 |
| --- | --- | --- | --- |
| 25개 템플릿 목록 | DB query 1 | 0 | 완료 상태 point read 1 + 제한 쿼리 1 (25개 문서) |
| 문자 준비의 템플릿 확인 | 페이지 GET 1 | 0 | 완료 상태와 해당 템플릿 point read 2 |
| 문자 준비의 학생/본문 저장 | 기존 경로 | 그대로 | 기존 저장·검증 그대로 |
| 유실 응답 후 템플릿 재시도 | 해당 없음 | GET으로 확인, 두 번째 PATCH 0 | 작업/자료 상태 검사·성공 기록 |
| idle 작업 서버 push | 해당 없음 | Notion 0 | 만기 작업 제한 쿼리 + 진행 상태 point read |

idle push를 매분 실행하면 하루 약 1,440번입니다. 빈 쿼리에도 최소 과금 단위가 있으므로 읽기 0원이라고 단정하지 않습니다. 빈 쿼리+상태 읽기를 각각 1RU로 가정하면 약 2,880RU/일이며, CPU/메모리·스케줄·로그 비용은 별도입니다. 이 값은 실측 RU가 아닙니다. 실제 문서 크기·인덱스 스캔·30일 사용량과 Query Explain을 배포 후 확인해야 합니다.

실제 네트워크 지연, Cloud Run cold start, Firestore 청구 단위·저장량·비용, 클라우드 예약 실행은 미측정입니다. 브라우저 실제 화면/실자료 이전·반영도 미확인입니다.

## 복구와 백업의 한계

이번에는 템플릿 텍스트의 버전 이력과 선택 복원, 불변 반영 요청의 실패 복구를 구현했습니다. Firestore 자체 손실·잘못된 대량 삭제에는 이력만으로 충분하지 않습니다. 독립 백업/PITR/분리 DB 복원 시험은 클라우드 설정과 비용 확인을 거쳐 C-3/D에서 적용합니다. 백업이 활성화됐다고 표시하지 않습니다.

## 검증과 유지한 것

별도 파일럿 저장소 double은 트랜잭션 read-before-write, 직렬화, 원자적 commit 실패, 순서/제한/cursor와 호출 카운터를 제공합니다. 운영 Firestore emulator/실제 서비스 검증을 대체하지 않습니다.

검증 대상: dry-run 쓰기 0, 25/105건 pagination·catch-up·중단 재개, 공통 잠금, 중복 명령, stale revision, 앱 저장과 작업의 원자성, 응답/성공 기록 유실, 새 수정의 대기 작업 대체, 충돌 값 갱신/확인, 보관/404 보존, 이력 복원, 관리자 접근, 클라이언트 차단, worker enable/secret, 조회 전환 후 기존 문자 payload/권한 보존입니다. UI는 SSR 마크업과 mount 요청 0을 검사합니다.

환경변수 검증 테스트의 등록 목록은 3개 신규 서버 설정에 맞춰 확장했습니다. 기존 검증을 제거하거나 완화하지 않았습니다. 기존 테스트의 동작 기대값은 유지했고, 새 테스트를 추가했습니다.

최종 검증: `npm run lint`, `npm test` 590개 전부 통과, `npm run build` 통과. Node ESM workspace import 통과. 비활성 로컬 worker는 `/health` 200과 `/run` 503 `TEMPLATE_WORKER_DISABLED` 확인 후 종료했습니다. 클라우드 배포·실자료 검증은 하지 않았습니다.

기존 일지/성적/일정 저장·반영, 자동 회차, 권한 확인, 학생 캐시 정책, 학부모 리포트·PIN, 실제 문자 발송 transport, Make, Notion API 버전(2022-06-28)은 변경하지 않았습니다. 기존 CSS @import 위치 및 500kB bundle 경고는 별도 문제로 남깁니다.

# 체크포인트 10 B — Bati 규약 부분 확인과 모의 발송 준비

2026-10-06. A hotfix 8까지의 전체 누적 변경을 포함합니다. 실제 Bati 연동/문자 전달 검증 완료를 뜻하지 않습니다.

## 확인된 규약과 미확인 항목

운영 Vercel 환경변수 이름을 조회했으나 BATI_* 등록 항목은 없었습니다. 비밀값은 복호화/출력하거나 환경변수를 변경하지 않았습니다. Notion 학생 DB의 발송버튼 수식 속성은 확인했지만 연결 도구가 formulaCode 본문을 validation_error로 거부했습니다. 사용자가 주소를 숨긴 수식을 제공했습니다.

확인된 GET query 키는 다음 12개입니다.

| 키 | 의미 |
|---|---|
| 보호자연락처 | 수신 번호; 사용자 설명과 수식 일치 |
| 메시지템플릿선택 | 선택한 템플릿 |
| 학생 호칭 | 학생 호칭 |
| 내용 | 본문 후보 입력; 실제 문자 액션의 연결은 미확인 |
| 강의명 | 수강 과목 |
| 수강료 | 수강료 |
| 납부기한 | 납부 안내 |
| 등록상태 | 등록 상태 |
| 수강시작일 | 수강 시작일 |
| 학년 | 학년 |
| 학생연락처 | 학생 연락처 |
| 보호자이름 | 보호자 이름 |

사용자는 평소 Notion 완성된 문자본문으로 확인했다고 설명했습니다. 하지만 수식은 완성된 문자본문이라는 query 키를 보내지 않습니다. Bati가 내용 값을 그대로 발송하는지, 템플릿을 치환하거나 Notion을 다시 읽는지는 작업 설정으로 확인해야 합니다. 12개 키 확인을 최종 문자 본문 매핑 확인과 동일하게 취급하지 않습니다.

Bati 공식 웹훅 안내에는 GET query/POST, 선택적 보안 헤더, 데이터 매핑과 GET 완료 페이지가 있습니다. 계정 공통 접수 성공 응답 규약은 확인하지 못했습니다. Bati 루트 화면에 읽기 접근을 시도했지만 로그인 화면으로 이동해 실제 작업 설정은 읽지 못했습니다. 로그인/작업 실행/웹훅 테스트는 하지 않았습니다.

## 수정

- batiTransport.ts로 요청 구성·설정 검증·응답 판정을 분리했습니다. 수신 번호/본문 키, 요청 방식, payload 종류 및 확인된 응답 규칙이 있어야 발송할 수 있습니다. 임의 2xx 성공 추정은 제거했습니다.
- body-only는 확인된 단순 번호+본문 작업용, legacy-student는 수식과 같은 12개 키용입니다. legacy-student는 GET/보호자연락처/내용 조합만 허용합니다. POST_JSON은 실제 작업이 JSON POST를 받는다고 확인한 경우에만 사용합니다.
- 준비 시 선택한 템플릿 제목과 당시 학생 정보를 고정해 연동 정보로 보관하고 미리보기에 표시합니다. legacy-student의 내용 값은 앱에서 최종 확인한 본문입니다. 기존 Notion 수식의 숫자/날짜/관계형 문자열 표현과 Bati의 추가 치환까지 동일하다고 주장하지 않습니다. 실제 매핑이 이 방식에 맞는지 확인 전 운영에서 사용하지 않습니다.
- 설정이 없으면 발송 버튼을 비활성화하고 서버도 preflight에서 거부합니다. 옛 문자 요청에 legacy 연동 정보가 없으면 새 초안을 준비해야 합니다. 설정 거부 시 send lock이나 외부 호출을 만들지 않습니다.
- 응답은 확인된 정확한 HTTP 상태, 정확한 텍스트 또는 JSON 경로/값 일치로 판정합니다. status 규칙은 그 상태만으로 접수가 보장되는 실제 규약이 확인된 경우에만 설정합니다. 200 HTML/실패 JSON/리디렉션 등을 임의 성공 처리하지 않습니다.
- 결과에는 HTTP 상태 및 accepted-rule/response-unconfirmed/transport-failure 분류만 보관합니다. 원시 응답/웹훅 주소/헤더 비밀값은 보관·반환하지 않습니다. accepted는 접수이며 실제 도착 성공이 아닙니다.
- 본문 생성·저장·미리보기·별도 최종 확인·발송 버튼을 유지합니다. 저장 후 새 ID의 초안으로 수정할 수 있고 기존 이력을 보존합니다. sending/uncertain의 자동 재발송이나 자동 잠금 해제는 없습니다.
- 번호 변경/연락처 변경 중/소속 검증, 같은 번호+본문의 중복 잠금, 응답 유실 및 결과 저장 실패 후 재전송 차단을 유지합니다.

## 서버 설정 준비

| 환경변수 | 설정 기준 |
|---|---|
| BATI_WEBHOOK_URL | 실제 기존 HTTPS 웹훅, 서버에만 저장 |
| BATI_MESSAGE_PARAM | 실제 본문 입력 확인 후 설정; 수식 후보는 내용 |
| BATI_RECIPIENT_PARAM | 확인된 보호자연락처 |
| BATI_WEBHOOK_METHOD | 수식은 GET. POST_JSON은 실제 JSON POST 확인 후에만 선택 |
| BATI_PAYLOAD_MODE | 실제 매핑에 맞춰 legacy-student 또는 body-only, 기본값 없음 |
| BATI_RESPONSE_RULE | 확인된 규약 JSON. 미확인 상태에서는 비워 발송 차단 |
| BATI_SECURITY_HEADER_NAME/VALUE | 실제 요구 헤더를 서버에 설정. 없다고 확인하면 두 값 모두 비움 |

응답 규칙의 형식만 설명하는 모의 예시입니다. 실제 Bati 응답이 아닙니다. 확인 없이 운영 값으로 복사하지 않습니다.

```json
{"kind":"status","status":202}
```
```json
{"kind":"text","status":200,"equals":"mock-accepted"}
```
```json
{"kind":"json","status":200,"path":["result","accepted"],"equals":true}
```

실제 문자 액션의 최종 본문 일치, SMS/LMS 선택·길이 및 GET 요청 길이 제한도 확인해야 합니다. 본문을 자동으로 잘라 보내지 않습니다.

## 검증

전체 483개, Bati 모의 전용 24개, 타입 검사, native 서버 import, 프로덕션 빌드 통과. 기존 큰 번들/Firebase mixed import 경고는 남아 있습니다.

모든 발송 테스트는 가짜 transport를 사용합니다. 한글/줄바꿈/이모지/&, +, %, 0원과 번호의 첫 0, 12개 키, GET/POST JSON/헤더, 응답 일치/미확인/HTML 200/실패 JSON/시간 초과/리디렉션, 중복 클릭, 같은 본문의 새 ID 중복, 부분 실패·응답 유실·결과 저장 실패·번호/소속 변경을 검증했습니다. 재실행은 npm run test:bati이며 실제 Bati로 보내지 않습니다.

운영에서는 Notion 속성 정보, 공개 Bati 안내, Vercel 환경변수 이름과 로그인 필요 여부만 읽었습니다. 실제 Notion 본문 수정/문자 발송/웹훅 호출/배포/Make 변경은 없었습니다. 숨겨진 비밀 URL을 복원·추정하지 않았습니다.

## 남은 확인과 인계

기존 노션 발송버튼이 연결된 Bati 작업에서 다음을 읽어야 합니다.

1. 우측 하단 트리거: GET/POST, 보안 헤더 유무, query 키의 데이터시트 매핑.
2. 문자 발송/솔라피 액션: 수신 번호 태그, 문자 내용 태그/수식. 내용인지 완성된 문자본문인지, Notion 재조회/추가 치환 여부.
3. 접수 성공 HTTP 상태/응답 본문 또는 공식 규약, 실제 전달 성공을 확인하는 이력 위치.

확인이 어려우면 작업 설정 화면을 주소·비밀값·실제 번호를 가려 보여 주거나 로그인된 화면에서 읽기 확인을 이어갈 수 있습니다. 실행/웹훅 테스트는 실제 문자로 이어질 수 있어 이번 단계에서 누르지 않습니다. 실제 번호와 본문을 확인한 사용자의 명시적 승인 전에는 실제 발송하지 않습니다.

B 준비 코드를 전달한 뒤 멈춥니다. 실제 발송 규약은 부분 확인 상태입니다. 다음 재개 때 C를 준비하더라도 문자 시나리오가 대체 완료/중단 대상이라고 판단하지 않습니다. Bati 설정 정보가 제공되면 남은 규약 검증을 이어갑니다.
